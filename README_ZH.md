# LiteGrip Studio

[English](README.md) | **简体中文**

**LiteGrip Studio** 是 LiteGrip 两指自适应夹爪的 PyQt5 上位机：开合、按位置拖动、力控夹持、速度设定、
状态与故障监视、实时曲线，以及完整标定页。

同进程直接 `import litegrip` 走 SocketCAN，没有跨语言桥。没有硬件时后端可切到内置
仿真被控对象，**全部交互都能跑通**——仿真不是界面占位，它跑的是与真机同一套运动
状态机。

## 🚀 快速开始

```bash
./run_litegrip_studio.sh sim        # 仿真，不需要硬件
./run_litegrip_studio.sh selftest   # 自检：不需要 Qt、不需要硬件
./run_litegrip_studio.sh test       # 测试套件
./run_litegrip_studio.sh gui        # 真机，通过 SocketCAN
./run_litegrip_studio.sh build      # 打包成单文件可执行程序
```

脚本里所有路径都加了引号——本仓库目录名带空格。解释器与 SDK 路径可用环境变量覆盖：
`PYTHON_BIN`、`LITEGRIP_SDK_PATH`。脚本默认用 `python3`，所以 Qt 装在虚拟环境里时，把
`PYTHON_BIN` 指过去：

```bash
PYTHON_BIN=.venv/bin/python3 ./run_litegrip_studio.sh sim
```

其余参数原样传给程序，例如 `./run_litegrip_studio.sh sim --log-level DEBUG`。
`-h` 看全部子命令。

### 接真机

**接口不用你自己起。** 点连接时控制台会先看一眼 `can0`，只在它确实不对（没 up、比特率
不对）时才动手，而且只动这一处：

- 提权走 `pkexec`，也就是桌面自己的授权框。**这个进程从不接触密码**，因此也不会把它
  写进日志。
- 已经配好的接口：不运行任何特权命令，**不弹授权框**。这是为了让你即使自己起过接口，
  每次连接也不会被打扰。判断「配好」不只看 up 标志和比特率，还看控制器的 `can state`
  ——**总线关闭（BUS-OFF）的接口这些字段全是正常的**，但它发不出任何帧，要让这种情况也
  被修掉。
- 配置时带 `restart-ms 100`：控制器进了总线关闭之后 100 ms 自己重开。不带它（内核默认
  0）就是**永远躺着**，之后每次发帧都返回 ENETDOWN，而 `connect()` 只是开 socket 不会
  报错——错误要等到第一个真的发帧的动作（使能）才冒出来，你看到的就是一句内核文案
  「网络已断开 errno 100」。
- CAN FD 接口：只报告、不改动。SDK 自己按接口 MTU 判断 FD 并通信，而「改回经典 CAN」
  会把同一条总线上的其他节点一起改掉。
- 真碰上 ENETDOWN 时，**它会被当成链路问题而不是电机问题**：提示里直接写接口名和
  `ENETDOWN`，并让你检查适配器与接线后重新连接。内核的这个 errno 和驱动器故障码
  完全是两回事（驱动器的码只有 0/1/9/0xA/0xB/0xC），照原样转述只会把人引到 24V 上去。
- 授权被取消、`can0` 不存在、`ip` 报错：**照常尝试连接**，只在日志与横幅里说明。
  这一步永远不会成为连不上的原因——接口本来就可能由别的东西管着，只有连接本身知道
  链路到底通不通。

接口由 unit file 或脚本管、不想被弹框的，用 `--no-can-setup` 关掉这一步；比特率不是
1 Mbit 的用 `--can-bitrate` 指定。

手动做的话，等价的命令还是这三条：

```bash
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 1000000 restart-ms 100 fd off
sudo ip link set can0 up
./run_litegrip_studio.sh gui
```

**首次接真机先从标定页跑一遍引导式标定，再动滑块。** 探测一结束结果就写盘。手指反过来装的夹爪
（张开时编码器角度变大）先勾上「反向装配」，或者干脆用手动两点标定——方向由操作者
自己按的按钮给出。若标定页显示 `FACTORY` 或 `BLOCKED`，先标定，不要靠勾选覆盖去动。

## 🖥️ 界面

四个标签页，外加常驻的连接栏（连接 / 断开 / 使能 / 失能 / 清除故障 / 急停复位）、
急停按钮和日志 dock。

| 页 | 内容 |
| --- | --- |
| 控制 | 位置滑块、全部张开 / 全部闭合、停止（保持位置）、松力（可手掰）、速度、夹持力、夹持 / 放开 |
| 状态 | 遥测表、温度、故障与清除、链路健康 |
| 曲线 | pyqtgraph 位置与力实时曲线（力的纵轴自适应） |
| 标定 | 来源横幅、文件操作、引导式 / 手动两点标定向导、闸门 |

**Esc 是应用级快捷键**，spinbox 有焦点或模态框弹出时依然生效。

### 滑块

需求的核心。三个视觉元素，两个独立的值：

| 元素 | 来源 | 含义 |
| --- | --- | --- |
| 手柄 | 用户拖动；非滑块发起时 = 实测 | 被命令的目标 |
| 目标细线（青） | 上一条命令 | 正走向哪里 |
| 实测三角（绿粗） | 遥测 | 爪子真实位置 |

左端是闭合点、右端是张开最大点，右侧等宽读数区显示实际 / 目标 / 误差。**夹爪移动时
进度条实时刷新**：开合按钮驱动时手柄跟着实测走，拖动时手柄跟手而实测标记自己动
（否则手指底下的滑块会被遥测拽回去）。默认松手才发命令，与 litearm-studio 的
`onValueChange` / `onValueCommit` 切分一致；「拖动时实时跟随」可打开。

实时跟随之所以安全，是因为每条运动命令都过限速参考发生器：拖出一个 120 mm 瞬移，
夹爪也只以设定速度走过去。

滑块两端各有一个**一键到底**的按钮，放在它们要去的那个端点旁边：

| 按钮 | 命令 | 去哪 |
| --- | --- | --- |
| 全部闭合（左） | `Close()` | 行程 0.0 mm，即标定记录到的闭合位置 |
| 全部张开（右） | `Open()` | `limits.max_stroke_mm`，即量程顶端（比记录到的张开极限内缩 1 mm） |

两个命令都走限速参考发生器，不是瞬移；按住期间随时可以「停止」或急停接管。悬停提示
里写着具体毫米数，标定一到就刷新——在读到标定之前提示**不报数字**，因为那时任何一个
毫米数都不是这台夹爪的。提示报的是**量程**（`max_stroke_mm`）不是标定文件记录的跨度：
按实测行程推导 mm/rad 之后这两个数不一样，报跨度会让人去找那段根本到不了的行程。

夹持力框里，**夹持 N** 的正下方还有一个**放开**：从夹爪**现在的位置**再张开 10 mm
（`RELEASE_OPEN_MM`），用来松开夹住的物体。它量的是**实测**位置，不是上一条命令的目标——
夹取本身就是朝行程 0 点顶过去并按力封顶，目标永远是闭合端，所以「目标 + 10 mm」等于命令
夹爪回到物体里。已经在量程顶端时它是原地不动（`move_to_mm` 内部 clamp），不是报错。
它是一条毫米命令，因此和张开 / 闭合 / 夹取一样受闸门管；标定不可用时能松手的是
**松力（可手掰）**和**停止**。

### 力曲线：纵轴自适应

力曲线原来是定在 40 N 额定值上的，那说的是这台机构**允许**做什么，不是它**正在**做什么：
12 N 的夹持画在纵轴下三分之一，而夹持内部那点起伏——判断夹爪是在稳定还是还在爬——只有
几个像素。现在纵轴每次重画时按窗口里的数据重新拟合：

- 向上取整到 1 / 2 / 5 × 10ⁿ（10 N、20 N、50 N），读数才有参照点；
- **峰值永远在图内**，超出就立刻开轴；
- 两侧峰都缩到轴的 3/4 以内才收轴，避免 8.6 N（→10 N）与 8.7 N（→20 N）在台阶边界上
  以 25 Hz 来回翻；
- 下限 2 N（正负各 1 N）：空载时那点制动扭矩只有零点几牛，轴贴上去会把噪声放大成满屏
  波形，看起来像在夹东西。

力的符号保留（SDK 的力矩没有符号保证），所以轴是**跨零**的：负的制动扭矩不会被切掉。
位置曲线的纵轴不做这件事——它按行程定标，这样同一段运动在任何夹爪上看起来都一样。

## 📐 标定：文件从哪来

这是设计时专门确认过的一个问题，答案不是二选一。SDK 的 `load_calibration()` 是
**两级回退**：

1. **用户标定文件**（`$LITEGRIP_CALIB` 或 `~/.litegrip/litegrip_calibration.json`）
   ——由 `calibrate_*()` → `save_calibration()` 写出，**这才是这台夹爪的参数**。
2. **出厂标定文件**（SDK 包内 `litegrip/factory_calibration.json`，只读）
   ——**兜底**。

所以：**上位机用的是标定结果文件，出厂文件只是兜底**。但这个过程有几个坑，上位机
因此自己读文件判定来源，而不是只看 SDK 的返回值：

- **兜底是静默的**。两种情况 `load_calibration()` 都返回 `True`，只有一条 `log.info`
  能区分。对真机意味着毫米读数系统性错掉而界面看不出来。
- **SDK 不强制标定**。`connect()` / `enable()` 都不会自动加载。不加载就用
  `GripperConfig` 默认值 `pos_closed_rad=0.0 / pos_open_rad=1.14`，而实机标定值是
  **闭合数值更大**（出厂 `0.114 / -1.491`，示例用户文件 `1.776 / -0.064`）。映射式
  `mm = (pos_closed_rad - position_rad) * rad_to_mm` 方向**恰好相反**，会算出负毫米并
  朝错误方向顶到硬限位。
- **`load_calibration()` 会覆盖 `kp` / `kd` / `grasp_torque_threshold`**，且字段读取
  没有保护——坏文件会抛 `KeyError`。

次序 `zero_rad <= open_rad` 正是 SDK 默认值 `(0.0, 1.14)` 的样子，上位机仍然靠它认出
「没标定过」。但次序本身不是结论：同样两个数、同样顺序，既可能是一台反向装配的夹爪，
也可能是一份把两个极限记反了的文件，靠算术分不开。所以上位机改为从这两个角度**读出**
装配方向（`Limits.direction`），所有换算、夹紧与速度前馈都用它，反向装配的夹爪因此可以
端到端正常使用；一份「反着写」的文件是**告警**、需要拿实测读数去确认，而不再是拒绝理由。
真正拒绝一份文件的是下面的 `frame_mismatch`，它根本不看次序。

以上全部是**读文件**得出的判断，而文件可以完全自洽却描述着另一台夹爪——只要它是对着
另一个编码器零点标出来的（换了台机器，或者同一台拆装重标之后）。行程、系数、方向全都
对，闸门判成「用户标定」，而操作者看到的每一个毫米都整体偏一个常数。文件里没有任何
东西能揭发这件事，只有实测角度能：**实测 rad 落在标定行程之外超过
`CALIB_MISMATCH_RAD`（0.15 rad）时，闸门判 `BLOCKED`**，并把实测值和行程区间一起报出来。

之所以要留 0.15 rad 的容差：止于红线而不到硬限位的标定（推荐的那一种）会让停在硬止挡上
的夹爪**合法地**待在自己可命令行程之外，本机这个余量最大 0.0866 rad；而零点错帧的偏差
是弧度级的（实测那一次 1.885 rad）。0.15 rad 卡在两者中间，既不误关闸门，也漏不掉。

这项检查发生在**实测角度已知之后、发帧之前**。放在发帧前不是选择而是必需：位置一旦被
`clamp_mm` 夹进行程，落在行程外的实测值和停在行程端点的实测值就再也分不开了，夹出来
的那个数看起来还完全合理。真机上这就是「一使能就夹紧」的成因。

闸门三态：`READY`（用户标定、无问题）/ `FACTORY`（需勾选「我了解风险」）/
`BLOCKED`（缺失，或零点不属于本机，**永不可覆盖**）。**闸门逻辑在 worker 里而不在
UI 里**——UI 能禁用控件，但拒绝必须发生在发帧之前。

另外：标定文件由 worker **在连接时**加载，不在启动时。这样来源判定和闸门描述的
永远是真正交到 SDK 手里的那个文件，而不是命令行当时说的那个。

换标定会作废循环里握着的每一个毫米。位置按新帧**重新读一次**（读数当初是后端用当时
那套限位换算出来的），正在保持或运动的目标就地**重新锚定**（一个用旧帧毫米表达的意图
没有诚实的换算方式）。少了这两步，载入一份*正确*的标定会让轴立刻朝新行程的另一端出发。

探测出来的结果先只在内存里（`in_memory_unsaved`），**此时仍然拦着闸门**——要先看清
测到了什么，再决定它是不是往后的运动依据。一次跑到头的标定因此**自己写盘**，不用再等
一句话：两次「记录」本身就是「要一份标定」的请求，让轴一直锁着、逼操作者去猜还要按第三次，
只会让一份已经完成的标定看起来像控制台坏了。存盘之后由后端把刚写下的文件**读回来**，
来源才转成 `user_file`、闸门才转 `READY`。真机与仿真两个后端都是这样：仿真若只写
不回读，操作者标定完、保存完，闸门还关着。

自动写有两件故意不做的事。一是不写没通过校验的结果：它要覆盖的是一份能用的标定，
宁可让操作者拿到一个拒绝运动的控制台，也不让它在自己刚说过不可用的数字上运动。二是
不覆盖 SDK 自带的出厂文件——那是随包发布、描述某台具体夹爪的数据。留在页面上的
「重新保存标定…」只为剩下那一种情况：写文件本身失败，比如目录只读或磁盘写满。

### 使能：先读到位置，再保持

`get_state().position_rad` 在收到第一帧状态之前是 `0.0`，而 `to_mm(0.0)` 落在行程**中间**某个看起来完全合理的
位置上。所以「使能后就地保持」如果发生在第一帧之前，保持的其实是一个电机从没报过的
角度：真机上这一条把夹爪直接送去了闭合限位。

现在的位置读数有两个状态，`TelemetryFrame.position_mm` 用 `None` 表示**还没有实测**——
不是 0。worker 只在自己数到过状态帧（`_rx_frames > 0`，与闸门、链路判活同一个信号）之后
才给出数；此前：

- **使能**后不保持，而是松力（`kp=kd=tau=0`）。零增益不需要位置，是这个窗口里唯一诚实的
  指令；第一帧到达后自动转成「在实测位置保持」并记一条日志。
- 停止 / 退出零重力 / 清除故障 / 闸门重新打开时若要「就地保持」，规则相同：
  没有实测就松力。
- 运动请求被拒，理由写明「尚未读到位置；电机还没回报过状态帧」。
- 界面一处都不显示数字：滑块不画实测三角也不动手柄，读数、状态页、状态栏、标定页与曲线
  都写 `—`（曲线记 NaN，线段断开）。0.00 mm 是闭合位，是个位置，而且是错的那个。

判活用的 `_rx_frames` 偏保守——SDK 自己的 `enable()` 内部会轮询，它收到的那一帧我们数不到
——所以这个窗口可能比必要值多几个 tick。往「拒绝运动」的方向偏，是唯一正确的偏法。

### 引导式探测的两条规则

探测是全应用里唯一被允许做两件「别的动作都不许做」的事的动作，两条都由它的目的决定：

- **标定存在之前就能动**——它正是产生标定的那一步。
- **标定存在之后可以走到标定行程之外**——它找的是硬止挡，而硬止挡按定义就在红线之外。

第二条曾经是缺的：`stream_frame` 的行程检查只看「有没有可用标定」，不看这一帧有没有
一个这项检查能判断的目标，于是任何一份有效标定都会把探测关进它自己要测量的那段行程里，
最后把「能命令到的最后一步」记成张开极限——一个读起来像成功测量的错答案。现在这类帧
显式声明自己不受门禁约束（`ungated=True`）：探测的步进（它找的止挡就在红线之外），以及
根本不携带目标的帧——松力、零重力、探测结束时留下的驻留，后者的位姿就是编码器刚报出的
那个角度。非受控帧仍然拒绝非有限值和负增益：那两个无论标定怎么说都是错的。

这个标志按「帧是什么」而不是「谁发的」命名，这一点对长期存在的状态同样成立：松力可以
一直开着，它放宽的范围不会随时间变大，因为它放宽的是一个「刚度为零、没有目标可言」的帧。
在此之前只有一个按第一个调用者命名的标志，而关门禁时的松力——正是文件坏掉时操作员最需要
的那个状态——被这道门禁拒绝了。

探测还必须知道**夹爪往哪边张开**，而这件事读文件读不出来——文件正是它要产生的东西。
它先把夹爪走进行程的张开止挡、再走向闭合止挡；如果是反向装配的夹爪，按 SDK 的方向走会
顶到错误的止挡上去，把两端记反——这样得到的标定能校验通过、能保存，然后让夹爪反着动。
所以方向在探测开始前由操作者声明（标定页上的「反向装配」，作为
`StartGuidedCalibration.reversed_mount` 传给 worker）；标定页同时显示**原始编码器角度**，
因为毫米数是拿那份正被怀疑的标定算出来的。

探测靠「读到的角度不再变化」判断到了止挡，而这同一个信号也意味着「没有帧到达电机」和
「反馈断了」——后两种情况下它会把两个极限记在同一个位置，然后报出行程异常（真机上出现过
`行程异常: 两个极限落在同一个位置 (-1.370650 rad)`，两个数字一模一样就是这个原因）。状态机在
里面分不出这三种情况，所以改由 worker 在外面看着：

- **帧没发出去**：`stream_frame` 连续 `PROBE_REFUSED_FAIL_S`（0.5 s，是 1.8 s 堵转判定窗口的
  一小段）返回 False → 中止并报「位置帧连续 N s 未能发出，电机没有收到任何指令」。
- **连接 / 使能 / 链路 / 故障**：每次 tick 先看这四项，任一不对立即中止，并说清是哪一条。

中止时**把探测记下的每一步判定都写进日志再报结论**——失败的探测里，那几行就是全部真相。

探测量的是硬止挡间距（两个硬止挡，不是红线之间的距离）；量出来的弧度是 mm 换算系数的
分母，分子是操作员量出来的行程，见「已知限制」。

### 手动两点标定

引导式探测要求两个止挡够得着、也判得出来。够不着的时候——连杆紧、行程不在 SDK 以为的
地方、或者轴根本不肯走一步——就用手动向导：全程零力矩，操作者自己把两片手指掰到两个
极限。**一开始标定轴就进入零重力、并且明说**；结束时把轴收回来，走哪一条出口都一样，
取消也算——整段过程操作者的手都按在手指上。引导式探测不这么办：它自己把手指开进止挡，
得独占这条轴。

- **两个带标签的按钮，不是一个。** 先记张开极限，再记闭合极限，后者即 0 mm。按钮上的
  标签就是操作者对「哪一端是零」的全部回答，所以按错步骤的那一次会被**明确拒绝**，而不是
  被当成「该记的那一端」收下：两个角度对调之后，上位机的每一项检查都会通过，夹爪却反着动。
- **不在后台采样。** 记下的角度是按下按钮之后那个控制周期的读数，也就是手停下来之后的
  第一个读数。SDK 的零重力模式是「扫一遍取极值」，那量到的是**手恰好扫过**的那段行程：
  掰到一半就松手的夹爪同样像一份标定，而且两个极限都没有名字，文件说不出哪一端是 0 mm。
- **不需要声明装配方向。** 方向由标签给出，所以两种装法都记得对，装配方向就是那两个
  角度最后长成的样子。两个极限记在同一个位置会被报出来而不是收下——那样一份文件会把整段
  行程的每一个毫米都算到同一个角度上。
- **读数先验后用。** 超出 SDK 自身合理范围的值、或者一个控制周期内动得比机构物理上可能的
  还多的值，会被丢弃而不是记下：丢帧会让 SDK 缓存的当前位置停在 `0.0`，它在该范围之内，
  又恰好是误读时**张开**极限会落到的位置——那一个数刚好能让整段行程静默地反过来。被丢掉的
  读数如果落在某次按键上，那次按键也一并作废：操作者按下时所在的角度，正是读不出来的那个。
- **每次等待都有上限**：`TWO_POINT_TIMEOUT_S`（每个点 5 分钟）。整个过程轴都是零力矩的，
  而一台「使能着、又软着」搁置的控制器，就是一只会落到下面东西上的夹爪。失败或取消的探测
  保持零力矩；只有走完全程的那一次才把轴交回位置控制，用 SDK 退出零重力时的那组增益——
  写文件失败时交回的是**编码器报出的那个角度**，因为毫米级的保持只能来自那份仍然存疑的
  限位。

## 🏗️ 架构

三条 SDK 约束决定了整体结构，都是读源码核实过的：

1. **SDK 完全不是线程安全的**——全包零 `threading`、零锁，所有运动方法在调用者线程
   里跑 200 Hz 阻塞循环，共用同一个 socket 和 `MotorState`。⇒ 单个 `GripperWorker`
   (`QThread`) 独占 SDK，GUI 线程永不触碰，跨线程调用直接抛 `RuntimeError`。
2. **`control_mit_stream()` 没有中断钩子**（`protocols/can_bus.py:342` 是裸 `while`），而所有
   SDK 便捷运动方法最终都走它。⇒ **不用这些方法**，自己用 `send_mit_frame` + `poll`
   跑 5 ms tick，急停检查才在循环里。
3. **`move_at_speed()` 每次调用固定补 20 帧保持**（`gripper.py:1117`）。⇒ 想「边移动边
   实时回显」不能把它切小段反复调，每段会卡 100 ms。

```text
src/litegrip_studio/
├── constants.py        # 所有策略数字都在这里，可脱离 Qt/SDK 单测
├── units.py            # mm↔rad、行程、限位、clamp（纯函数）
├── calibration.py      # 标定文件解析/校验/来源判定/保存策略（纯 + 文件系统）
├── settings.py  telemetry.py  logging_setup.py  version.py  selftest.py
├── backend/
│   ├── __init__.py     # GripperBackend ABC + _claim() 线程归属断言
│   ├── real.py         # 只用公开 SDK 原语
│   ├── plant.py        # 纯仿真被控对象：step(dt)，无线程无 sleep
│   └── sim.py          # plant + 实时节拍 + 故障注入
├── core/
│   ├── commands.py     # frozen dataclass 命令集
│   ├── profile.py      # 抗积分饱和的限速参考发生器（纯）
│   ├── motion.py       # MotionFSM: IDLE/HOLD/SERVO/GRASP/HOLD_FORCE/FAULT
│   ├── calibration_fsm.py
│   └── worker.py       # GripperWorker(QThread)：独占 backend，200 Hz tick
└── ui/
```

分层原则：**策略数字**全在 `constants.py`；**纯逻辑**（`units` / `profile` /
`calibration` / `plant` / FSM）不依赖 Qt、SDK、线程，用普通 pytest 单测；**碰 SDK 的**
只有 `backend/`；Qt 层薄。

后端抽象只暴露 FSM 需要的原语，**绝不暴露 SDK 便捷方法**——这保证同一套 FSM 在真机
和仿真上跑，仿真才真正验证逻辑而不是并排站着。

### 参考发生器

每 tick 把参考**锚定在实测位置**上，这是抗积分饱和的关键。若用内部积分器递推，堵住时
参考跑到目标、误差与 `kp·err` 持续增长，会无限夹紧：

```python
v_allow = min(speed_mm_s, sqrt(2*acc*max(rem - TOL_MM, 0)))   # 停车距离限速
v_ref   = slew(v_ref, v_allow, acc*dt)                        # 梯形
q_cmd   = measured + sign*min(v_ref*dt, rem)                  # ← 锚定实测，绝不过冲
```

梯形只多三行，换来起停无速度阶跃（无电流尖峰）、有停车距离（不会全速靠伺服刹车）。

### 什么时候算「撞上了」

位置移动中撞到东西要停，靠的是**丢失位移**：参考发生器另外积分一条「本来该走到哪」的
理想路径（`virtual_mm`，只用于比较、绝不下发，所以不会积分饱和），实测跟不上它就说明
前面有东西。窗口是 1 mm。

但这条判据**是个模型**：它假设机构在巡航段跟得住参考。跟不住的机构——摩擦大、连杆紧、
带了负载、或者给的速度下 `kp` 偏小——会在**走得完全正常**的同时攒出同样这 1 mm。此时
停车不是安全措施而是故障：操作员看到的是「松手后它动两下就停」，而不是走到指的位置。

所以在纯位置移动（没有力设定值）上，这个 1 mm 还要**加上一条旁证**才算撞上：实测速度
低于参考速度的 25%（`CONTACT_STILL_RATIO`）。判据是**比例**不是绝对速度，所以 5 mm/s
和 150 mm/s 一样适用；真的顶住时夹爪速度必然塌下来，照样抓得住；真的一动不动的情况由
堵转计数和**到位超时**兜底，两者都没变。

这个数字有实测来源：仿真里 0.3 Nm 库仑摩擦的机构，20 mm/s 的移动在走到 2.7 mm 时被判
「位置未随时间变化」，而它当时正以**设定速度的 87%** 在走。加上旁证后同样的移动能走完。
`tests/test_motion_fsm.py::TestWhetherAGapIsAnObstruction` 把两种情况都钉住了。

### 关闭与安全

关闭三层，保证电机不留在使能态：`run()` 的 `finally` → `zero_torque→disable→disconnect`；
`app.aboutToQuit` 同调用（幂等）；`SIGINT`/`SIGTERM`。`terminate()` 兜底**本质不安全**
（可能停在半帧），日志里明说而不假装安全。

三种停止语义，因为 SDK 单一的 `stop()` 不够：

| 按钮 | 行为 | 电机 |
| --- | --- | --- |
| 停止 | FSM→HOLD 在当前 rad，参考复位 | 保持使能 |
| 松力 | 持续发 `kp=0,kd=0,tau=0`，可手掰 | 保持使能、可反驱 |
| **急停**（红 / Esc） | `zero_torque()→disable()` 并**闩锁**，复位前拒绝一切运动 | 失能 |

急停走 `threading.Event` 而不是命令队列——它不能被排队，tick 在 FSM 之前检查。
另有 GUI 看门狗：GUI 每 500 ms 发心跳，worker 3.0 s 收不到即视为上位机已死，零力矩
并失能。

## 🛠️ 开发

测试不需要硬件，也不需要安装 SDK：

```bash
./run_litegrip_studio.sh test
# 等价于
QT_QPA_PLATFORM=offscreen <venv>/bin/python3 -m pytest tests/ -q
```

`pytest-qt` 未安装，用的是普通 pytest + session 级 `QApplication` fixture +
`PyQt5.QtTest`，`QT_QPA_PLATFORM=offscreen`。`conftest.py` 把 SDK 与 `src/` 插进
`sys.path`，所以 SDK 没安装也能测。

自检 `--selftest` 只跑纯逻辑（单位换算、标定方向判定、零点错帧拦截、被控对象收敛、
运动到位、力矩上限、急停失能），**不 import Qt**——最需要它的机器正是 Qt 坏掉的那台。
测试里有一个子解释器断言这一点。

### 关于 SDK 依赖

SDK **故意不是**已解析的依赖：它是本仓库旁边的检出目录，其唯一声明的依赖
`eclipse-zenoh` 在库代码里从未被 import，因此主路径是把检出目录放进 `PYTHONPATH`
——启动脚本就是这么做的。想走安装路线也可以：

```bash
python -m pip install -e ../lite-grip --no-deps
```

（若 venv 里的 `setuptools` 低于 61，它无法解析 PEP 621，这时不要加
`--no-build-isolation`。）

### 打包

```bash
./run_litegrip_studio.sh build      # → dist/litegrip-studio
```

`--collect-data litegrip` 是必须的：SDK 用 `dirname(litegrip.__file__)` 找出厂标定
文件，在 `sys._MEIPASS` 下也成立，但没有这个参数文件不会进产物，出厂回退随之失效。

版本戳在构建时写进 `_version.py`，**构建结束即从源码树删除**（它也已 gitignore）。
留着它会让之后每次源码运行都拿着上一次构建的号自称，而那个号里的 git hash 可能早就
和工作区对不上了。戳只活在产物内部，所以源码运行一律报告 `+source`。

`_version.py` 里的号**不是发布版本号**。发版由 semantic-release 按提交历史自动完成，
git tag 是唯一的事实来源，`pyproject.toml` 里的 `0.0.0-semantic-release` 是占位符，
不要手改。

## ⚠️ 已知限制

- **自动标定 `calibrate()` 首版不提供**。它虽然无 stdin 依赖，但不可中断且会跑约 24 秒
  运动——与其提供一个急停无效的 24 秒窗口，不如只上引导式与手动两点标定。
- 出厂标定是**兜底而非替代**：出厂文件用在别的夹爪上不会崩，只会让毫米读数静默地错。
  标定页把「文件自带比例尺推出的行程」拿来看，但只在它连数量级都不对时告警
  （`STROKE_MIN_MM` / `STROKE_MAX_MM` 之外）。这条判定**不能**收紧到与实测行程比较：
  SDK 与旧版控制台写出的文件一律带「标称行程 ÷ 跨度」，那个标称是 SDK 自己的默认值而不是
  录制那台夹爪的测量值，60 mm 的夹爪和 120 mm 的夹爪写出来是同一个数——收紧只会让每一份文件（包括本机自己
  那份）都告警，而一直亮着的告警等于没有告警。区分「文件属于哪台夹爪」靠的是实测角度的
  帧校验（`frame_mismatch`）与推导系数的合理区间。
- 力上限取机械额定 40 N；理论 100 N（10 Nm × 10）只作灰色不可选注释展示。
  要改只需动 `constants.FORCE_MAX_N` 一处。
- **毫米换算系数由「两个角度 + 实测行程」推导，不读文件自带的 `rad_to_mm`。**
  SDK 把那一项写成「标称行程 ÷ 行程」，所以这台机器上每一份标定文件都写着 120 mm 的
  系数，不管那两个角度是在哪台夹爪上录的。载入这样一份文件，一台实际行程 85 mm 的夹爪
  会读出 120 mm，而滑块只覆盖其中一段，两端永远走不到——「0-120 中间截取一段」就是这么
  来的。文件里的两个角度是测量值，系数是派生量，所以由 `units.derive_scale()` 推导：
  `(实测行程 + SPAN_INSET_MM) / 行程`。本机是 `(85 + 1) / 1.681925 = 51.13 mm/rad`，
  于是记录到的两个极限跨 86.00 mm，滑块量程 0…85 覆盖整段行程，量程顶端落在记录到的
  张开极限内侧 1 mm。
- 行程（`constants.DEFAULT_TRAVEL_MM`，85.0 mm）是**本机夹爪的实测值**，是常量而不是偏好。
  它决定两件事：mm 换算系数与滑块量程，所以一个能被改成别的数的控制台会把每一个毫米
  读数都算错，而界面上看不出任何异常。2026-09-28 之前它确实可以在标定页上改，那天被改成了
  10 mm：推导出的 8.0 mm/rad 低于 `RAD_TO_MM_MIN`，于是校验把一份好标定判成 problem，
  门禁拒绝运动——控制台既动不了，也说不清为什么。现在没有任何入口能改它：`--travel-mm`
  已删除，退役的设置键 `calibration/travel_mm` 会在控制台打开时从旧 ini 里清掉，把这台
  控制台移到另一台夹爪上意味着改这个常量并重新探测。
  保存标定时，写进文件的是**这个推导出来的系数**（SDK 从自己的 config 写文件，控制台在
  保存前把 limits 推进 config），也就是控制台实际运动用的那个数：再读回来时自洽，
  交叉核对（SDK 应用的系数 == 文件里的系数）才有意义。探测自己算出的那个系数留在
  `raw` 里作展示与比对，它表示的是「当时设定的标称行程 ÷ 跨度」，不是这台夹爪的宽度。
- **量程顶端为什么内缩 1 mm**：探测是在 40 N 压力下把张开极限压出来的，连杆在这股力下
  让出约 1 mm，所以记录到的张开极限比机械终点略过一点。直接命令到记录极限，等于每次全开
  都把止挡压一下；内缩 1 mm 到达的是同一个物理位置，只是不带那一下。闭合端不做内缩：
  探测在那一端压到的是两指相触的位置，本来就没有余量，而且「0 就是标定出来的 0 点」。
